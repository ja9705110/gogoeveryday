# PROJECT 030 · 系統設計

> 這份文件對應需求中的六項先行交付：系統架構、資料庫結構、十天流程、狀態轉換、故事分支、第一關原型。
> 為避免洩漏，本文件與整個 repo **不包含終章禮物的內容**；終章尋寶只存在資料庫，由管理後台設定。

## 1. 整體系統架構

```
┌──────────── 手機瀏覽器（PWA）────────────┐        ┌──────────────── Supabase ────────────────┐
│ index.html  玩家端（終端/區域/培養艙/…）   │  RPC   │ Auth：Email 驗證碼（OTP）／管理者密碼     │
│ admin.html  管理後台                       │ ─────▶ │ Postgres：遊戲引擎（plpgsql）             │
│ js/ar.js    MindAR 影像追蹤（iPhone Safari）│        │   ・時間判定 now() + Asia/Taipei          │
│ sw.js       離線外殼 + Web Push 接收        │        │   ・狀態轉換 / 分支 / 養成 全在伺服器     │
└────────────────────────────────────────────┘        │   ・RLS：玩家只能經 RPC 動自己的檔案      │
          ▲                                           │ Storage：evidence / gifts（私有 bucket）  │
          │ Web Push                                  │ pg_cron（每 5 分）：逾期判定、產生提醒    │
          └──── Edge Function push-dispatch ◀──────── │ pg_net → push-dispatch（VAPID）           │
                                                      └───────────────────────────────────────────┘
```

* **前端不判定任何結果**：答案、提示、揭露內容放在 `levels.secrets`，玩家角色沒有任何讀取權限；前端只把操作送到 RPC。
* **時間**：所有判定使用 `now()`（伺服器時間），以 `settings.tz = Asia/Taipei` 換算日界線。玩家手機時間只用於畫面倒數顯示。
* **管理者保護**：管理功能是 `admin_*` RPC，函式內 `assert_admin()` 檢查 `admins` 表；內容表以 RLS `is_admin()` 保護。前端只是介面。
* **測試模式**：管理者建立的 `is_test` 檔案有自己的 `sim_offset`（模擬時間 = now() + offset）；所有測試 RPC 都會檢查 `is_test` 且屬於自己，正式玩家的檔案無法被時間偏移或強制操作。測試檔案不推播。

## 2. 資料庫結構（`supabase/migrations`）

| 表 | 用途 |

| `settings` | 生日日期、時區、提醒時間、每日提醒上限 |
| `admins` / `admin_emails` / `allowed_players` | 管理者與受邀玩家名單（不在名單的信箱無法建立檔案） |
| `profiles` | 遊戲檔案（正式 1 份／帳號；測試可多份，含 `sim_offset`） |
| `levels` | 第 1–11 區內容：`config`（主線）、`alternate`（替代路線）、`secrets`、`ar_fallback`、`on_complete` / `on_alternate_complete` / `on_missed` 效果、自訂開放／截止時間 |
| `symbols` | 十枚符號：名稱、頻率數字、分階段揭露的 lore |
| `player_levels` | 每區狀態、結果（ON_TIME/ALTERNATE）、變體、`missed_at`（觸發器保證不可回寫）、步驟進度 |
| `flags` | 事件旗標與選擇（`choice:*`） |
| `inventory` | 符號（含殘響版本）、隱藏物品、樣本 |

| `evidence` | 照片／錄音／文字／選擇／掃描紀錄，含審核狀態 |

| `notifications` / `notification_prefs` / `push_subscriptions` | 通知（`unique(profile, dedupe_key)` 防重複）、偏好、勿擾、推播訂閱 |
| `portrait_gift` | 形象照邀請函與風格選擇 |

## 4. 任務狀態轉換規則

```
LOCKED ──(server now ≥ open_at)──▶ AVAILABLE ──(open_level)──▶ IN_PROGRESS ──(所有必要步驟完成)──▶ COMPLETED(ON_TIME)
   │                                   │                              │
   └───────────────(server now ≥ close_at，未完成)──────────────────────┘
                                        ▼
                     missed_at 寫入（永久）＋ on_missed 效果＋MISSED 事件＋通知
                        ├─ 有替代路線 → ALTERNATE ──(完成)──▶ COMPLETED(ALTERNATE)，missed_at 保留
                        └─ 沒有替代路線 → MISSED（不可再遊玩）
```

* 判定時機：每次玩家 RPC 前 `refresh()`，以及 pg_cron 每 5 分鐘 `cron_tick()`（不需要玩家開網頁）。
* `close_at` 預設為次日 00:00（不含），即當天 23:59:59 為最後時刻；可在後台為單一關卡自訂開放／截止。
* 步驟也可設定時段（`window`），例如 D5 夜間花苞。
* 逾期時原路線進度封存在 `data.main_archive`，替代路線從頭開始；`missed_at` 由觸發器保護，即使把時間往回調也不會恢復。
* 佐證狀態：`PENDING_REVIEW`（已提交・等待審核）→ `APPROVED` / `NEEDS_MORE`；補充後舊紀錄標為 `REPLACED`；關卡逾期時未補的 `NEEDS_MORE` 變成 `OVERDUE`。選擇與掃描紀錄由系統直接驗證（`APPROVED`）。

## 5. 故事分支與觸發條件

條件語法（`eval_cond`）可巢狀：`{"flag":"x"}`、`{"flag":"choice:fork","eq":"keep"}`、`{"missed":3}`、`{"ontime":2}`、`{"done":4}`、`{"item":"photo_old"}`、`{"stat":"exploration","gte":2}`、`{"form":"岔形"}`、`{"all":[…]}`、`{"any":[…]}`、`{"not":…}`。

可用統計（不是評分）：`consistency`、`ontime`、`completed`、`missed`、`exploration`（隱藏物）、`observations`、`streak`、`max_streak`、`breaks`。

| 觸發 | 影響 |
|---|---|
| D1 錯過 → `lab_dark` | D2 變暗（變體 `dim`）、守夜人只在黑暗中出聲 |
| D2 準時 → `watcher_met`；錯過 → `watcher_left` | D3 / D5 / D7 守夜人在場或只剩紙條（不同場景、不同對話）；終章台詞不同 |
| D3 照片 `photo_old` | D7 凹槽隱藏點出現；D7 錯過則照片被奪走（`remove_items`） |
| 隱藏物 ≥ 2（`exploration`） | D5 藤蔓後隱藏溫室、D7 柱子後隱藏房間 |
| 錯過 ≥ 2 | D4 鏡子出現裂痕；**D8 出現第三扇「沒有名字的門」**與專屬機關（伺服器計時停留） |
| D6 / D8 / D10 選擇 | 終章系統報告逐句不同 |
| 觀測連續 ≥ 5 / 中斷 ≥ 2 | D10 核心脈動規律或不規律（場景變體） |
| 管理者特殊事件 | 任意旗標／物品，可被任何關卡的 `when` 使用 |

變體在玩家**第一次進入**該區時判定並寫入 `player_levels.variant`（之後不會因後續資料而跳動）；步驟層級的 `when` 每次即時判定（例如選了哪扇門）。

**養成樣本**：四種觀測（探索／保存／調整環境／靜置）分別推動分岔、殼層、光度、根深；連續觀測累積節律（規律的對稱與脈動），中斷累積偏移並在樣本上留下紅色痕跡（另一種生長，不是死亡或歸零）。形態名稱 = 修飾（節律／漂流／斷續）＋主形（岔形／燈形／年輪形／深根形／未定形），完全由 `observations` 計算；畫面由這些參數與歷程以程式繪製。

## 6. 第一關原型

第 1 區「接入」已可完整遊玩（主線與替代路線），流程：系統開場 → 配電箱（6 個開關，提示「無法再被拆開的位置」→ 2、3、5）→ 終端機（讀牆上停住的時鐘 10:30）→ 樣本出現 → 前往培養艙完成第一次觀測 → 觀測日誌（文字，進入審核）→ 歸檔，取得符號「起」。桌下有隱藏標籤（探索）。
錯過則進入「備用通道」：全黑場景、手電筒搜索螢光圓圈、破碎時鐘文字線索，取得「殘響・起」。

* `supabase/tests/engine_test.sql`：88 項伺服器端情境測試（第一關遊玩、答案不外洩、步驟順序、RLS、陌生帳號、測試模式隔離、模擬錯過、替代路線、物品遺失、變體、伺服器計時、時間倒轉不可逆、事件紀錄不可改、動態回放、提醒去重與上限、無替代路線的 MISSED、終章、樣本中斷）。
  執行：`bash supabase/tests/run.sh`（需要本機 Postgres 16，見 README）。
* 管理後台「測試模式」：建立測試檔案 → 設定模擬時間／+1 天 → 套用完成／錯過／替代完成 → 模擬排程 →「以此檔案遊玩」用玩家介面實際走一遍。
